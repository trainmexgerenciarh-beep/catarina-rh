## Antecedente comprobado y límites

La Iteración 01 dejó `test:processing` INCOMPLETO. Una prueba posterior de requisitos del premio recibió texto no vacío que falló en `JSON.parse`; no se guardó el contenido de esa respuesta ni su metadata de terminación. Los mensajes anteriores de error no permitían distinguir transporte, truncamiento, JSON mal formado o esquema inválido.

No se puede probar retrospectivamente que todas las interrupciones anteriores tuvieron idéntica causa. Tampoco había evidencia para atribuirlas a credenciales, latencia o una caída transitoria.

## Investigación y causa reproducida

Se ejecutó una reproducción de solo lectura con el catálogo real y la configuración original: `gemini-flash-latest`, límite de 128 tokens, `thinkingBudget: 0`, MIME JSON y esquema.

Metadata segura obtenida, sin texto del proveedor, firmas, teléfonos ni IDs:

| Caso ficticio | Modelo resuelto | Terminación | Tokens de pensamiento | Tokens de salida | JSON válido |
| --- | --- | --- | ---: | ---: | --- |
| Pago del premio | `gemini-3.8-flash` | `MAX_TOKENS` | 122 | 2 | No |
| Requisitos del premio | `gemini-3.8-flash` | `STOP` | 93 | 7 | Sí |

**Causa técnica reproducida:** el límite compartido de 128 tokens podía agotarse con pensamiento, aunque la configuración histórica intentara desactivarlo mediante presupuesto cero. El alias había resuelto a un modelo cuyo control vigente es por nivel de pensamiento. Una generación truncada puede contener texto, pero no JSON completo. El tratamiento local no inspeccionaba `finishReason` antes de parsear y ocultaba esa causa bajo una excepción genérica.

El caso de requisitos pudo completar en la reproducción; esto confirma variabilidad, no invalida el fallo histórico. La configuración anterior no aseguraba espacio suficiente y el parser no distinguía respuesta incompleta de JSON inválido.

Referencias técnicas consultadas:

- [Google: structured outputs](https://ai.google.dev/gemini-api/docs/structured-output): JSON Schema, campos obligatorios, nulabilidad y validación local de valores.
- [Google: thinking y límite de tokens](https://ai.google.dev/gemini-api/docs/thinking): el límite incluye pensamiento y puede truncar la salida.
- Declaraciones del SDK oficial instalado `@google/genai`: `responseJsonSchema`, `thinkingLevel` y metadata de terminación de `generateContent`. No se migró a otra API ni proveedor.

## Corrección mínima

1. Se mantiene el alias y el SDK oficial. Se usa nivel de pensamiento bajo y límite de 1024 tokens, que incluye pensamiento y salida. No se agregan reintentos ocultos ni cambios de proveedor.
2. Se solicita MIME `application/json` con `responseJsonSchema`: objeto con exactamente `id_servicio`, obligatorio, ID del catálogo activo o `null`, sin propiedades extra.
3. Se exige una sola candidata terminada en `STOP` antes de interpretar el texto. `MAX_TOKENS` se informa como `OUTPUT_TRUNCATED`; otras terminaciones incompletas o bloqueadas son fallo técnico.
4. Se usa parseo JSON estricto y se valida forma y tipo localmente. No se eliminan cercas Markdown, no se completan fragmentos y no se “salva” un ID desde texto inválido.
5. Solo `null` explícito en una respuesta válida representa falta semántica de correspondencia. ID ausente/tipo incorrecto, ID inventado/inactivo y catálogo vacío fallan técnicamente.
6. Los errores llevan clase y código seguros: configuración, integración, formato o catálogo. Se conserva solo estado HTTP numérico cuando existe; no se almacenan ni imprimen respuestas, mensajes del proveedor, causas crudas o secretos.
7. El webhook conserva su acuse y HTTP 503 ante fallo de procesamiento; su log puede distinguir el código seguro. HMAC, GET y acceso a colaboradores no cambian.
